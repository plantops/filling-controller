# SP01 Specification

Canonical v0.1 behavior for one spout.

## Sequence

```text
WAIT_PERMISSIVE
-> WAIT_FILL_POSITION
-> BAG_ACQUIRE
-> BAG_VERIFY
-> TARE_READY
-> COARSE_FILL
-> FINE_FILL
-> CUTOFF
-> SETTLE
-> WAIT_DISCHARGE
-> PUSH
-> COMPLETE
```

Every state has an entry action, exit condition, timeout and fault path.

## Speed-adaptive discharge position

A fixed time delay from one position sensor shifts the physical bag release angle when rotor speed changes.

Use two fixed angular references on the same pass:

```text
sensor A -> measure elapsed monotonic time -> sensor B -> predict command time -> PUSH
```

Let:

```text
ΔθAB       known angular spacing A -> B
T_AB       measured time A -> B
ΔθBT       angular spacing B -> optimum physical discharge point
T_actuator measured command -> physical release delay
```

Then:

```text
T_B_to_target = T_AB × ΔθBT / ΔθAB
command_delay = T_B_to_target - T_actuator
```

This makes the command timing scale automatically with current rotor speed.

Implementation uses monotonic microseconds, not a software loop counter.

Important geometry rule: sensor B must be early enough that `command_delay >= 0` at the fastest allowed rotor speed. If the physical optimum point is 355° and the pusher has non-zero response delay, a sensor B located exactly at 355° is too late for same-pass compensation. Put B upstream of the command point (for example A around 340° and B around 350°, with actual positions commissioned on the machine), or use a different strategy based on a previous-pass speed estimate.

The actual sensor angles and actuator delay are commissioning data, not hard-coded defaults.

## Timing context

At 2,000 bags/h with 8 spouts:

```text
bag interval       1.8 s
SP01 cycle         14.4 s
```

Actual state timing, discharge geometry and cutoff parameters come from bench and machine measurements.

## Hard rules

- one controller owns one spout;
- one control context commits all physical outputs;
- Wi-Fi/HMI never participates in cutoff, discharge timing or interlocks;
- control never blocks waiting for a Modbus reply;
- stale/invalid weight causes bounded abort;
- invalid discharge timing geometry causes a fault rather than a knowingly late push;
- safety/E-stop remains independent of firmware;
- hardware-specific channel/register details stay in adapters.
